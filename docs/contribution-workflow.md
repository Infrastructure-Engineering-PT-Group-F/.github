# Contribution Workflow

This workflow applies to all repositories in the
`Infrastructure-Engineering-PT-Group-F` organization. Repository-specific
`CONTRIBUTING.md` files may add local validation commands or tooling details,
but the issue, branch, commit and pull request rules below are the shared
baseline.

## Issues

Create an issue before starting any relevant change. Issues are part of the
assignment audit trail and should explain the context, scope, acceptance
criteria and validation evidence for the work.

Create the issue in the repository where the main change will happen:

| Change area | Repository |
| :--- | :--- |
| Organization profile, shared templates and cross-repository documentation | `.github` |
| Terraform, GCP/GKE, IAM, Workload Identity and bootstrap documentation | `infrastructure` |
| ArgoCD, Crossplane, tenant resources, platform add-ons and GitOps docs | `gitops` |
| Weather API, backend Helm chart, backend image and API documentation | `backend` |
| Vue/Quasar frontend, frontend Helm chart, private image and runtime config | `frontend` |

For cross-repository work, create one issue in each repository that needs a
change. Link the issues and pull requests by their full GitHub URLs. Track the
overall outcome from the issue in the repository that owns the main result.

Small release automation updates may be tracked by the release pull request
when the repository commit rules explicitly exempt release automation commits.
Security, secret handling, infrastructure, GitOps and user-facing behavior
changes should always have a normal issue.

## Branch Naming

Use short, descriptive branch names that identify the change type, issue number
and purpose:

```text
<type>/<issue-number>-<short-description>
```

Examples:

- `docs/3-contribution-workflow`
- `security/24-restrict-platform-appproject`
- `ops/10-gitops-runbook`
- `ci/50-gitleaks-secret-scan`
- `feat/39-tenant-provisioning`
- `fix/64-external-secret-drift`

Use branch prefixes that make the work area clear. Common prefixes are `feat`,
`fix`, `docs`, `ci`, `chore`, `security` and `ops`. Existing release-please
branches are generated by automation and do not need to follow this format.

## Commit Messages

Commits must follow Conventional Commits and reference the relevant issue:

```text
<type>(<optional-scope>): #<issue-number> <description>
```

Examples:

- `docs: #3 document shared contribution workflow`
- `docs(security): #24 document platform AppProject restriction`
- `docs(ops): #10 document GitOps troubleshooting steps`
- `ci: #50 add Gitleaks secret scanning`
- `fix(chart): #31 set backend chart appVersion`

Use the commit types allowed by each repository's commitlint configuration:
`feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`,
`chore` and `revert`. The issue reference can also be in a footer, for example
`Refs #42` or `Closes #42`, when that reads better for a longer commit subject.
Do not use merge commits; keep repository history linear.

Release automation commits such as `chore(release): release 1.3.2` are exempt
only where the repository commitlint configuration explicitly allows them.

## Pull Requests

Open a pull request before merging into a main branch. Use the shared pull
request template and keep the PR focused on the linked issue.

Every PR should include:

- A concise summary of the change.
- A linked issue using `Closes #<issue>` when the PR completes it or
  `Relates to #<issue>` when it is partial.
- The affected repositories or components.
- Validation steps, including commands, CI runs, screenshots or GitOps/Kubernetes
  evidence where useful.
- Security considerations, especially confirmation that no secrets, tokens,
  kubeconfigs, private keys or `.env` files were added.
- Documentation updates or a short reason why documentation is not required.

Use PR titles that mirror the commit convention and include the issue number:

- `docs: #3 document contribution workflow`
- `feat: #39 prepare tenant provisioning prerequisites`
- `fix: #64 declare ExternalSecret extract defaults`
- `ci: #50 add GitOps Gitleaks secret scanning`

## Reviews

Before requesting review, self-review the diff and confirm that the PR template
is complete. Request a reviewer who understands the affected repository or
component.

Review expectations:

- Check that the PR scope matches the linked issue.
- Check that the change does not introduce plaintext secrets or unnecessary
  permissions.
- Check that validation evidence is sufficient for the change type.
- Check that documentation was updated when behavior, workflows or operations
  changed.
- For cross-repository changes, check that related issues and PRs are linked.

Material infrastructure, GitOps, security or application behavior changes should
be reviewed by another team member before merge whenever feasible. Documentation
or release automation PRs may be merged with lighter review if the change is
straightforward and CI passes.

## Definition of Done

A pull request is done when:

- The linked issue has clear acceptance criteria and the PR satisfies them.
- The branch and PR title follow the shared naming convention, except for
  generated release branches.
- Every relevant commit references an issue, except explicitly exempt release
  automation commits.
- CI passes or any skipped/unavailable validation is explained in the PR.
- Local validation was run where practical and the command output or result is
  recorded in the PR.
- No secrets, credentials, private keys, kubeconfigs or `.env` files were added.
- Documentation was updated or explicitly marked as not required.
- Related issues and pull requests are linked for cross-repository work.
- Reviewer feedback has been addressed.
- The issue is closed by the PR or updated with the remaining follow-up work.
